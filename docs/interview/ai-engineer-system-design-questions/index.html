Top AI & ML Engineer System Design Interview Scenarios

Key architectural scenarios, trade-off questions, and technical answers for AI Engineer and Applied Scientist system design interviews.

#Interview#System Design#RAG#Agents#Architecture
Focus Topic:AI Systems Design
Difficulty Level:Advanced

Preparing for an AI Systems Architect or Senior AI Engineer interview requires demonstrating a firm grasp of distributed systems, vector retrieval, GPU inference economics, and agentic control flow.

Below are high-frequency system design scenarios and reference solutions.

Scenario 1: Design a Production RAG System for 20 Million Financial Documents

Interviewer Prompt

“Design a search and question-answering system over 20 million regulatory filings, financial statements, and analyst reports. The system must guarantee citation fidelity, achieve sub-second response times, and support user-specific access control lists (ACLs).”

graph TD
    Ingest[Document Ingestion Pipeline] --> OCR[Unstructured PDF / Table Parser]
    OCR --> Chunk[Semantic & Table Aware Chunking]
    Chunk --> ContextSummary[Prepend Context Metadata]
    ContextSummary --> Embed[Dual Sparse & Dense Vector Generation]
    Embed --> Storage[(Qdrant / Milvus Cluster with ACL Metadata)]

    User([User Query]) --> Auth[JWT & User ACL Filter]
    Auth --> HybridSearch[Hybrid BM25 + Vector Search]
    Storage --> HybridSearch
    HybridSearch --> Rerank[Cross-Encoder Reranker Top 5]
    Rerank --> LLM[Streaming LLM with Inline Footnotes]

Key Talking Points to Hit

  1. Document Ingestion & Chunking: Do not use naive 500-character chunking. Mention table preservation (converting HTML/Markdown tables) and Anthropic-style Contextual Retrieval to prepend company/quarter metadata.
  2. Access Control Filtering: Explain why metadata filtering (pre-filtering by org_id and user_role in the vector DB payload) is safer than post-filtering after ANN search.
  3. Latency Optimization: Use an ANN index like HNSW with quantized vectors (scalar quantization SQ8 or product quantization PQ) for fast candidate retrieval, then rerank with a cross-encoder model.

Scenario 2: Prevent Multi-Turn Autonomous Agents from Runaway Looping

Interviewer Prompt

“You deploy an autonomous coding agent with shell execution and git tools. How do you detect and recover from infinite loops, hallucinated dependencies, or destructive commands?”

graph TD
    Agent[Agent Execution Loop] --> PreGuard[Pre-Execution Command Filter]
    PreGuard -->|Disallowed e.g. rm -rf| Abort[Block & Prompt Agent]
    PreGuard -->|Allowed| Sandbox[Isolated Container Sandbox]
    Sandbox --> OutputCheck[Output Monitor & Loop Detector]
    OutputCheck -->|Identical Output 3x in a Row| CircuitBreaker[Trigger Circuit Breaker]
    OutputCheck -->|Progress Made| Agent

Solution Architecture

  1. Episodic Loop Detection: Compute a rolling hash of the last 3 (Thought, Action, Output) tuples. If a loop is detected, inject a hard intervention prompt: “You are repeating the same failed command. Cease this approach and try an alternative.”
  2. Container Sandboxing: Run tool executions inside ephemeral Docker or gVisor microVMs with disabled internet access except for explicit package mirrors.
  3. Budget Caps: Enforce strict per-session token budgets and max-step timeouts (N=15N=15N=15).

Scenario 3: Memory Sizing for High-Concurrency LLM Inference

Interviewer Prompt

“How would you calculate whether a cluster of 8x H100 GPUs (80GB each) can serve a 70B parameter model with a 32k context window at 100 concurrent requests?”

Calculation Steps

  1. Model Weights: A 70B model in 16-bit (bfloat16) requires 70×2=140 GB70 \times 2 = 140\text{ GB}70×2=140 GB of VRAM.
  2. KV Cache per Token: With GQA (Hkv=8H_{kv} = 8Hkv​=8, d=128d=128d=128, 80 layers), memory per token is 2×2×80×8×128≈320 KB/token2 \times 2 \times 80 \times 8 \times 128 \approx 320\text{ KB/token}2×2×80×8×128≈320 KB/token.
  3. KV Cache for 32k context: 32,000×320 KB≈10.24 GB32,000 \times 320\text{ KB} \approx 10.24\text{ GB}32,000×320 KB≈10.24 GB per request.
  4. Total for 100 concurrent requests: 100×10.24 GB=1,024 GB100 \times 10.24\text{ GB} = 1,024\text{ GB}100×10.24 GB=1,024 GB.
  5. Total VRAM required: 140 GB+1,024 GB=1,164 GB140\text{ GB} + 1,024\text{ GB} = 1,164\text{ GB}140 GB+1,024 GB=1,164 GB.
  6. Total Available VRAM: 8×80 GB=640 GB8 \times 80\text{ GB} = 640\text{ GB}8×80 GB=640 GB.

Conclusion: The cluster cannot handle 100 concurrent full 32k requests in FP16 (1,164 GB>640 GB1,164\text{ GB} > 640\text{ GB}1,164 GB>640 GB).

Optimization Strategies:

  • Quantize KV cache to FP8 (slashes KV cache from 1,024 GB1,024\text{ GB}1,024 GB to 512 GB512\text{ GB}512 GB).
  • Use PagedAttention and chunked prefill to maximize GPU utilization.
  • Add Tensor Parallelism (TP=8) across the 8 GPUs to distribute model weights evenly (17.5 GB17.5\text{ GB}17.5 GB weights per GPU).

Frequently Asked Questions

What is the most common pitfall candidates make in AI system design interviews?

Focusing solely on model prompting while neglecting data pipelines, inference latency, memory bandwidth, caching strategies, and evaluation guardrails.

How do you answer questions regarding LLM hallucination mitigation?

Address it across three pillars: 1) Retrieval Grounding (hybrid search + cross-encoders), 2) Generation Constraints (strict schema validation, temperature 0.0), and 3) Post-Generation Verifiers (critic LLMs, citation cross-checking).
